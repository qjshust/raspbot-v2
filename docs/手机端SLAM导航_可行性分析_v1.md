# 手机端建图 / 看地图 / 设目的地 / 自动到达 —— 可行性分析

- 版本：v1（分析稿，不含代码）
- 日期：2026-11-19
- 前置文档：`docs/手机遥控_小程序可行性分析_v1.md`（遥控链路）、`docs/RASPBOT-V2_智能驾驶系统设计文档_v2.4.docx`（系统架构与工作包）
- 结论一句话：**能做，而且你的 v2.4 设计文档已经把这件事排进了 W3/W4（M2 建图、M3 定点导航）；手机端是整条链路上最容易的一环，真正的瓶颈是「底盘没有编码器」和「Nav2 参数要在这个麦轮车上重新调」——这两件事跟手机无关。**

---

## 0. 结论与边界

| 你想要的 | 能做吗 | 条件 / 代价 |
|---|---|---|
| 手机遥控小车**建图** | ✅ 能 | 需要一个能跑 `slam_toolbox` 的里程计输入（见 §5.1），以及手机摇杆（复用遥控方案） |
| 手机**实时看地图** | ✅ 能，而且最简单 | 服务端把 `/map` 渲染成 PNG，手机只画图和标记；1 Hz 刷新足够 |
| 手机**点图设目的地** | ✅ 能 | 发给 Nav2 `NavigateToPose`；触点坐标按地图元数据换算成世界坐标 |
| 小车**自动规划 + 避障到达** | ⚠ 有条件能 | 20 m² 室内、平坦地面、0.15 m/s、静态家具，成功率能到 90%；无编码器 + 2D 雷达 + 麦轮，遇到打滑/玻璃/低矮障碍会失败 |
| **跨楼层 / 户外长距离 / 高速** | ❌ 不在本期范围 | 需要 3D 雷达/高程地图、编码器、GNSS，属 P1/P2 |

**精度预期（写进验收，别写得更漂亮）**

- 单次建图（20 m²，闭环）：位置误差 <0.2 m（对齐设计文档 TC-05）
- 定点导航重复精度：**10–20 cm**（无编码器）；加编码器后可到 5–10 cm
- 不是「1–2 cm 级」的室内机器人；不要把扫地机那种定位精度当预期

## 1. 先对齐：你的设计文档其实已经覆盖了这件事

v2.4 里已定义 `WP-E 融合与里程计`、`WP-F 建图与定位`、`WP-G 导航与避障`，数据流也已冻结：

```
底盘 <--I2C--> raspbot_base --/odom_raw--> ekf_node --/odom--> Nav2 --/cmd_vel_safe--> raspbot_base
IMU  <--UART--> raspbot_imu --/imu/data----> ekf_node
雷达 <--USB---> lidar_driver  --/scan-------> slam_toolbox --/map--> Nav2
                                          \-> amcl（定位模式）
```

排期与验收也在文档里：W3 建图 → M2「室内地图可用」，W4 Nav2 → M3「定点导航闭环」，TC-05/06/07/08 是对应用例。

**所以真正缺的不是方案，是两样东西：**

1. **实现**：仓库里现在只有 `raspbot_base` 和 `raspbot_imu` 两个包，E/F/G 都还没落地（`base_node` 目前直接发 `/odom` 和 `odom→base_link`，还没拆出 `/odom_raw`）。
2. **手机层**：设计文档里**没有任何工作包覆盖「手机作为 HMI」**——没有话题/接口契约，也没有验收用例。这是本次分析要补的那一块（§6–§7）。

## 3. 手机在这个系统里的位置：HMI，不是控制器

这一点决定了后面所有设计：

```
┌──────────── iPhone ────────────┐
│ 小程序 / H5                    │
│  只做三件事：                  │
│   ① 显示地图/位姿/路径/状态    │
│   ② 采集触摸 → 指令            │
│   ③ 急停                       │
└──────────────┬─────────────────┘
               │ HTTP(地图PNG) + WS(状态/指令)
               ▼
┌──────────── Pi 5 ──────────────────────────────┐
│ hmi_gateway (新增，唯一新增进程)                │
│   /map → PNG    /tf → 位姿    /plan → 折线      │
│   /scan → 降采样点   Navigation action feedback │
│   ← goal / initialpose / mode / estop / 摇杆    │
│                                                 │
│ slam_toolbox 或 amcl  →  map→odom（唯一属主）    │
│ Nav2 (planner/controller/BT/costmap)            │
│ ekf_node → /odom + odom→base_link（唯一属主）    │
│ raspbot_base → I2C 0x2B → 电机                  │
└─────────────────────────────────────────────────┘
```

**关键推论：导航跑在车上，手机断电/锁屏/走出 WiFi 都不影响小车继续执行目标。** 手机只是「遥控器和仪表盘」。这带来两个好处：

- 手机端不需要低延迟，**4G 云中转在这个场景反而完全够用**（带宽 <100 KB/s、延迟 200–400 ms 对「点一下设目标」毫无影响）——和遥控视频那种毫秒级需求完全不同。
- 手机端 UI 可以做得「慢」一点：地图 1 Hz、位姿 10 Hz 就够。

## 4. 四个功能逐个判可行性

### 4.1 手机遥控建图

**可行**，本质是「遥控（已分析）+ 车上跑 slam_toolbox」，手机不需要额外能力。

条件：
- 手动速度上限建议 **0.12–0.15 m/s**，转向 ≤0.5 rad/s，否则扫描匹配来不及对齐、地图会重影（设计文档 NFR-01 的 20 Hz 控制器周期在这儿是够的，瓶颈是人开得快）。
- 建图时**关掉视频**（如果同时传图），把 CPU 留给 slam 与 planner。
- 建图结束要能「保存」，存到 `/mnt/ssd/maps/<名字>.pgm/.yaml`（文档已规划该路径）。

一个容易忽略的点：**建图过程中手机不能锁屏**（小程序挂起 → 摇杆断），所以建图页要 `setKeepScreenOn`，并且断连即停要生效（`/cmd_vel` 超时 0.5 s 已被 `base_node` 实现）。

### 4.2 手机看地图

**最容易，风险最低。** 核心决策：**不要**把 `OccupancyGrid` 原始数据发给手机让 JS 渲染。

理由：20 m² 的 5 cm 地图是 400×400=16 万栅格，小程序里解析成 JS 数组会有明显卡顿和内存抖动；而同样的图渲染成 PNG 只有 **5–20 KB**。

方案：Pi 端用 `cv2`/PIL 把 `/map` 渲染成 PNG（灰度 + 三色：未知/空闲/占用），1 Hz 推送；手机 `<image>` 或 canvas `createImage` 直接贴图，再叠加箭头/激光点/路径。

三个实现细节（都会真的踩到）：

- **`/map` 的 QoS 是 transient_local**。网关订阅时必须用 `TRANSIENT_LOCAL` + `RELIABLE`，否则只能等下一次更新，看起来像「没数据」。同理 `/scan` 是 best-effort，用错 QoS 会静默收不到。
- **坐标系翻转**：ROS 地图原点在**左下角、y 向上**，PNG 是**左上角、y 向下**。换算写错，点哪走哪会镜像。
  ```
  world_x = origin_x + px * resolution
  world_y = origin_y + (map_height_px - py) * resolution
  ```
- **地图尺寸别写死**：分辨率与尺寸随场景变化，每次随 PNG 一起下发元数据。

### 4.3 手机设目的地

**可行**，是个纯 JS 交互问题：
- 点图 → 像素 → 世界坐标（上面的公式）→ `PoseStamped`（`frame_id: map`）→ `NavigateToPose` action。
- 朝向：不强制，默认「朝向目标点」即可；需要精调时再提供「长按拖箭头」。
- 反馈：action feedback 里有 `distance_remaining`，10 Hz 显示「剩余 2.4 m」比进度条有用；`/plan` 话题给路径折线，2 Hz 下发就够。
- 失败处理：`NavigateToPose` 会返回结果码（超时/被取消/无有效路径/卡住），UI 必须显示**为什么失败**，否则用户只会以为「车坏了」。

### 4.4 自动规划与避障

**有条件可行**，这是全篇风险最高的部分，风险不在手机，在车：

| 风险 | 具体表现 | 对策 |
|---|---|---|
| 无编码器 | 打滑后位姿跳变，AMCL 跟丢，局部规划器抖 | 限速 0.15 m/s；短距离目标；必要时上 E1 编码器 |
| 麦轮侧滑 | 横移时轮子空转，odom 与真实运动不符 | 少用纯横移，优先差速式运动；调 `k_geom` 与死区 |
| 雷达盲区 | 扫描面离地约 **74 mm**（甲板 +34 mm，甲板距地约 40 mm）：玻璃、镜面、深色地毯、**低于 74 mm 的物体**基本看不见 | 超声补盲 + 物理防撞条 + 限定场地；不要把「避障」理解为「不会撞」 |
| 后向遮挡 | 云台立柱挡住正后方 ±12° | `laser_filters` 切掉后向扇区，或直接把后向从代价地图里排除 |
| 无悬崖检测 | 遇到楼梯/台阶会直接冲下去 | **必须**限定在无高差场地；需要跨房间就加 ToF 防跌落 |
| 无电量检测 | 低电量时电机功率下降、行为异常 | 加 INA219/分压采样（¥10 级），或严格限时 |

**验收就按设计文档的 TC-07/TC-08 来**：随机 5 个目标点成功率 ≥90%、路径中放 30 cm 障碍要在 0.3 m 前停住。这两个用例会把上面 6 条风险全部暴露一遍。

**如果 Nav2 调不动，有个务实的退路**：自研「A\* 全局规划 + 纯跟踪 + 前向雷达/超声停障」的小导航器，约 2–3 人日，没有行为树、代价地图、恢复行为，但在这个尺寸的车上**鲁棒性反而可能更好**。建议在 W4 中途评估一次：如果 Nav2 一周内过不了 TC-07，就走这条退路，别死磕。

## 5. 几个必须现在想清楚的技术判断

### 5.1 里程计：这是整件事的地基，也是唯一的硬缺口

没有编码器，意味着 `/odom` 只能靠「指令速度积分 + IMU 航向」。而 **slam_toolbox 和 AMCL 都要求 `odom→base_link` 存在，并且靠 odom 的位移量决定「什么时候处理下一帧扫描」**——odom 不可信，地图就会错位、重影、闭环失败。

设计文档 TABLE 47 已经给了三阶段路线，我的评估是：

| 阶段 | 做法 | 预期 | 建议 |
|---|---|---|---|
| 一 | IMU 航向替换积分航向，平移仍用指令速度 | 直线 2 m 误差 <5 cm（=2.5%，需标定 `pwm_per_mps`） | ✅ 先做，一天能出 |
| 二 | EKF 融合 + **雷达扫描匹配**兜底 | 20 m² 闭环 <0.2 m | ✅ 必做，这是 M2 的关键 |
| 三 | 编码器（AS5600 + TCA9548A + RP2040） | 接近常规移动机器人 | ⚠️ 建议在 W3 结束前决策要不要上 |

**我的意见：不要在 M2 之前上编码器，但要在 W3 结束时算一笔账。** 如果扫描匹配能稳定闭环，编码器就从「必需」降级为「加分项」；如果建图反复重影，那 3–5 天的硬件改造是唯一出路——继续在软件里调只会浪费更多时间。

另外提醒：里程计的**尺度因子**（`pwm_per_mps`）会随电量、地面材质、负载变化。同一张图今天准、明天偏 3%，这是正常的，别当成 bug 去追。

### 5.2 麦轮 + Nav2：默认配置一定不对

Nav2 默认按差速车规划，麦轮车要改两处：

- **控制器**：`nav2_mppi_controller` 支持 `motion_model: "Omni"`，是麦轮的正解；但它吃 CPU（Pi 5 上建议 1000 采样以内、15–20 Hz）。CPU 吃紧时可退化为「只走差速式运动 + DWB」，牺牲横移换稳定。
- **AMCL 运动模型**：用 `nav2_amcl::OmniMotionModel`，而不是默认的 Differential。
- **footprint**：车体 180×160 mm，但雷达托盘前伸 58 mm → 实际包络约 **238×180 mm**，足印必须把前伸算进去，否则会「车身过去了、雷达撞了」。
- **代价地图膨胀半径**：0.25–0.35 m 起调；太小贴墙蹭，太大进不了门。

### 5.3 `/cmd_vel` 只能有一个来源

手动摇杆和 Nav2 控制器都会发 `/cmd_vel`，同时发就是指令打架。两个办法：
- `twist_mux`（标准做法）：优先级 导航 > 摇杆 > 停车；
- 或者网关做模式门控：`teleop` 模式下不跑 Nav2、`navigating` 模式下忽略摇杆（并显式提示）。

选哪个都行，但**必须在契约里写清楚**，否则现场表现是「车一顿一顿的」，很难查。

### 5.4 每一次开机都要「告诉车它在哪」

AMCL 冷启动不知道位姿。三个层次，建议全做：
1. 保存上次成功位姿，启动时作为 `initial_pose` 初值（`set_initial_pose: true`）；
2. 手机端提供「长按地图拖箭头」手动设初始位姿；
3. 定位失败（协方差爆炸 / 匹配分低）时 UI 明确报警，而不是让车带着错位姿乱走。

### 5.5 手机断连时，车该继续还是停？

这是产品决策，不是技术决策：

| 模式 | 断连行为 | 理由 |
|---|---|---|
| 手动遥控 | **立即停**（已有 0.5 s 看门狗） | 人在环路里，失联必须停 |
| 自动导航 | **默认继续**，可选「失联 30 s 自动取消」 | 目标已下发，车有避障；半路停在走廊中间有时更危险 |

注意：**不要把遥控的看门狗逻辑套到导航上**，否则用户锁个屏，车就停在半路了。

### 5.6 算力：够用，但要克制

设计文档估「Nav2 + SLAM + 感知峰值约 2 核」，我认同这个量级，但要注意叠加：

- 已实测：`raspbot_base` 6.6%、`imu_node` 9.7%、`rplidar_node` 1.7%
- 新增估算：`slam_toolbox` 25–45%、Nav2 栈 120–200%、`hmi_gateway` 5–10%、视频（若开）10–20%
- 合计约 **2–3 核 / 4 核**，内存 8 GB 够（Nav2 约 0.6–1 GB）

建议：`governor=performance`、关掉不用的节点、视频只在需要时开、MPPI 采样数别贪。

## 6. 手机网关（新增，建议编号 WP-I / HMI）

现有契约只定义了 ROS 2 内部的话题与 TF。手机层需要一个**只消费、不拥有任何 TF**的新进程。

### 6.1 接口设计（HTTP 管图，WS 管状态与指令）

| 接口 | 方向 | 内容 | 频率/大小 |
|---|---|---|---|
| `GET /api/map.png` | Pi → 手机 | 渲染后的地图 PNG | 1 Hz，5–20 KB |
| `GET /api/map/meta` | Pi → 手机 | `{resolution, origin, width, height, frame_id}` | 变更时 |
| `WS /ws` 状态帧 | Pi → 手机 | 位姿、模式、导航状态、剩余距离、超声、CPU/温度 | 10 Hz，~300 B |
| `WS /ws` 激光帧 | Pi → 手机 | 降采样 360 点（极坐标） | 5 Hz，~2 KB |
| `WS /ws` 路径帧 | Pi → 手机 | `/plan` 折线点列 | 2 Hz，~1–2 KB |
| `POST /api/goal` | 手机 → Pi | `{x, y, yaw?}` → `NavigateToPose` | 事件 |
| `POST /api/initialpose` | 手机 → Pi | `{x, y, yaw}` → `/initialpose` | 事件 |
| `POST /api/mode` | 手机 → Pi | `mapping / localization / teleop / idle`（互斥，FR-F-04） | 事件 |
| `POST /api/map/save`、`/api/map/load` | 手机 → Pi | 地图存取 | 事件 |
| `WS /ws` 摇杆帧 | 手机 → Pi | `{vx, vy, wz}` 20 Hz（仅 teleop/mapping 模式） | 20 Hz，40 B |
| `POST /api/estop` | 手机 → Pi | 急停（发 `/cmd_vel` 零速 + `/estop`） | 事件 |

**为什么地图走 HTTP 不走 WS**：图片天然可缓存、可重试，`<image src>` 一行就能显示，不用在 JS 里做二进制分帧；状态走 WS 是为了 10 Hz 的平滑位姿。

### 6.2 网关必须遵守的契约纪律

- **不发布任何 TF**。`map→odom` 属主是 slam_toolbox 或 amcl（二选一），`odom→base_link` 属主是 EKF。网关重复发就会打架（设计文档 4.3 明确禁止）。
- **不改话题名、不改消息类型**；只新增进程和端口。
- 模式互斥在**网关**里强制执行（一个状态机），不要指望用户记住「先关建图再开定位」。
- `/map` 用 transient_local QoS；`/scan` 用 sensor_data QoS。
- 网关崩溃不能影响底盘：不要让它持有 I2C，也不要让它成为 `/cmd_vel` 的唯一通路（手动遥控和导航直连 ROS 2，网关只是入口之一）。

### 6.3 地图渲染（服务端做，20 行）

`OccupancyGrid` → `uint8` 数组 → 三色映射（未知 205 / 空闲 254 / 占用 0）→ PNG。20 m² 图耗时 5–20 ms，1 Hz 完全无压力。可选把 `/scan` 点直接烤进图里做「实时占位」，但没必要——手机叠加更灵活。

## 7. 手机 UI（小程序完全够用，这次不用为视频妥协）

上一份文档的结论是「小程序不适合当图传终端」。**但在 SLAM 场景里，这个短板基本不成立**：主体是 2D 地图 + 少量状态，不是视频流。8–12 fps 的视频在这里只是「辅助看一眼」，甚至可以不装。

交互清单（按手机屏幕从上到下）：

1. **连接**：IP/端口（默认 `192.168.50.98:8080`）、配对码、记住上次；扫描局域网设备可选。
2. **地图区**（占 ~65% 屏）：PNG 底图 + 机器人箭头 + 激光点 + 路径 + 目标标记；单指拖动平移、双指或按钮缩放、双击回中。
3. **模式条**：`空闲 / 手动 / 建图 / 定位 / 导航`，当前模式高亮，切换要二次确认（防误触）。
4. **摇杆**（仅手动/建图模式出现）+ 常驻**急停**大按钮。
5. **建图**：开始 / 结束并保存（弹名字输入）/ 放弃。
6. **定位**：地图列表、加载、「设置初始位姿」（长按拖箭头）。
7. **导航**：点图设目标、取消、重试、剩余距离与状态文案（失败原因必须具体）。
8. **仪表**：连接状态、IMU yaw、超声距离、CPU/温度、看门狗指示、电量（当前硬件没有，显示「不可用」或后加采样）。
9. **设置**：速度上限、是否显示激光点、是否开视频、日志导出。

### 小程序端的三个平台适配点（都不是坑）

- **双层 canvas**：底层画地图（1 Hz 重绘），上层画箭头/激光/路径（10 Hz 重绘）。单层全量重绘会闪。
- **触摸坐标换算**：`touch.x/y` 是 CSS 像素，canvas 有 `pixelRatio`，缩放/平移矩阵别忘了逆变换——点图偏移是这类 UI 最常见的 bug。
- **不需要 `web-view`、不需要 `live-player`**：这两个个人主体的限制在 SLAM 界面上完全不涉及。

> 开发顺序建议：**先用 H5 在浏览器里把网关协议和交互调通**（Chrome DevTools 比小程序真机调试快一个数量级），再把同一套渲染逻辑平移到小程序。两者共用同一个网关，不重复投入。

## 8. 带宽与延迟：这个场景非常宽松

| 数据 | 频率 | 大小 | 带宽 |
|---|---|---|---|
| 地图 PNG | 1 Hz | 5–20 KB | 5–20 KB/s |
| 状态帧 | 10 Hz | ~300 B | 3 KB/s |
| 激光点 | 5 Hz | ~2 KB | 10 KB/s |
| 路径 | 2 Hz | ~1.5 KB | 3 KB/s |
| 摇杆 | 20 Hz | 40 B | 0.8 KB/s |
| **合计** | | | **< 40 KB/s（约 0.3 Mbps）** |

结论：**这个 UI 在 4G 上也能跑**（延迟 200–400 ms 对「看地图、点目标」完全无感）。也就是说，上一份文档里「4G 远控要大动干戈」的结论，在 SLAM 场景下不成立——真要远控，加一个 MQTT/WSS 中转就够了，不需要视频链路那套投入。

反过来说：**不要给这个 UI 加实时视频**，一加就回到 2–3 Mbps，云中转的成本和复杂度立刻翻倍。

## 12. 明确做不到 / 不要承诺的事

1. **不是「放下去就能自己逛」**：需要先人工慢速建图，且建图质量决定后续一切。
2. **不是「绝对不会撞」**：2D 雷达在 74 mm 高度，玻璃、低矮障碍、悬空桌沿都可能漏；必须有人监护 + 物理防撞。
3. **不能跨楼层、不能下楼梯**（无悬崖检测，这是安全隐患，必须写进使用限制）。
4. **不能在动态人群里高速穿行**：10 Hz 雷达 + 0.15 m/s 的策略是「停下来等」，不是「绕开人群」。
5. **不要用开环 odom 做「精确对准充电桩/机械臂对接」**：那需要编码器 + 视觉，属另一类项目。
6. **地图会漂**：家具搬动、长时间使用后需要重建或重新定位，这是 SLAM 的常态。

## 14. 一句话总结

**手机端不难——地图是 2D 图形，不是视频流，小程序完全扛得住；难的是让这台没有编码器的麦轮车产出可信的里程计，以及让 Nav2 在 74 mm 高的 2D 雷达上不撞东西。** 你的 v2.4 文档已经把路线和验收写好了，现在缺的是 E/F/G 的实现和一层没人认领的手机网关。先花两天用键盘遥控 + slam_toolbox 跑一次建图闭环，整件事的可行性就从「不确定」变成「有数据」。
