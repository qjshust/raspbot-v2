## 1 概述

### 1.1 目的

设计文档第 10 章给出了 11 条集成验收用例（TC-01～TC-11）与分级原则，但不足以支撑"每个工作包独立验收 + 整车集成 + 实车场景"的完整测试。本方案把验收要求展开为**可执行、可判定、可追溯**的三级测试方案，回答四个问题：

- **测什么**：从 FR / NFR / TC 追溯到具体用例，共 169 条（软件 69、系统 53、实机 47），覆盖单元到外场；
- **怎么测**：每条用例给出前置条件、操作要点、测量方法、判定阈值；
- **判什么**：先冻结判据（第 4 章），避免"跑完了不知道算不算过"；
- **留什么证据**：bag 白名单、记录表、目录与命名规范，保证结论可复现、可回归。

### 1.2 范围

**覆盖：**

- WP-A 底盘驱动、WP-B IMU：已实现，本轮即可测（单元、契约、台架、标定、运动精度）。
- WP-C 雷达、WP-D 相机、WP-E 融合、WP-F 建图、WP-G 导航、WP-H 平台：用例已定义，交付后按状态解锁执行。
- 系统级：启动、话题与 TF 契约、建图定位、导航避障、时延、长稳、安全降级、环境适应、存储与数据完整性。
- 实机：台架悬空、低速场地、20 m² 室内场地、户外平整步道（仅 M4 阶段）。

**不覆盖（本期明确不做，避免测试范围蔓延）：**

- Hailo-8 视觉推理链路（本期设计文档 §1.4 已排除，仅保留硬件健康检查的历史结论）；
- 编码器改装、GNSS、机械结构改造、真实机动车道行驶；
- 微信小程序正式上线（仅做链路可行性验证 V1～V8）；
- hailo_pci 内核 `rwsem` WARN 的根因定位（已知问题，测试时过滤噪声）；
- 机械件疲劳寿命、IP 防护、EMC 认证。

## 2 测试策略

### 2.1 测试层级

测试分层遵循"能离线测的不上台架，能台架测的不上路"的原则，越靠下越便宜、越靠上越真实。

| 层级 | 目的 | 环境 | 用例前缀 | 门禁（不通过则不许进入下一层） |
|---|---|---|---|---|
| L0 静态与构建 | 代码可编译、可读、依赖声明完整 | 开发机 / CI | `SW-S` | 零新增警告、lint 通过、依赖完整 |
| L1 单元 | 纯逻辑正确：运动学、积分、解析、滤波 | 开发机，无 ROS 无硬件 | `SW-U` | 纯逻辑行覆盖 ≥80%，全绿 |
| L2 组件 | 单节点行为：启动、参数、异常路径、发布频率 | 开发机 / Pi，mock 硬件 | `SW-G` | 节点可启停、异常不崩溃 |
| L3 契约 | 话题、QoS、frame_id、TF、参数名与冻结契约一致 | Pi，真硬件或多节点 mock | `SW-C` | P0 契约项全过 |
| L4 集成（SIL/HIL） | 多节点协同、bag 回放、链路连通 | Pi + 真传感器 + mock 底盘 | `SW-I` | 单发布者、TF 树完整 |
| L5 系统 | 端到端功能与性能：建图、导航、时延、长稳、降级 | Pi + 真车 + 场地 | `SYS-` | P0 全过、P1 ≥80% |
| L6 实机场景与外场 | 真实运动精度、标定、场景任务、续航、边界 | 真车 + 场地 / 户外 | `CAR-` | 各里程碑验收判据 |

**左移要求**：任何工作包提测前，`SW-S`、`SW-U` 必须已通过——这是 CONTRACTS §6 DoD 的"脱离真车的测试"条款，不允许用实车测试替代单元测试。

### 2.4 判定与准出准则

**优先级定义：**

| 优先级 | 含义 | 准出要求 |
|---|---|---|
| P0 | 安全、契约、核心功能；不通过则不可交付、不可上路 | **100% 通过** |
| P1 | 主要功能与性能指标 | ≥80% 通过，未通过项须有批准的缺陷单与规避措施 |
| P2 | 体验、诊断、可运维性 | 可延后，登记为技术债 |

**分级准出：**

| 阶段 | 准出条件 |
|---|---|
| 包级提测（M1a） | `SW-S`+`SW-U` 全绿；对应 WP 的 `SW-C` P0 全过；README 五要素齐全 |
| 集成（M1） | `SW-C`/`SW-I` P0 全过，TF 唯一；`CAR-C` 标定完成；**直行 2 m 误差 <5 cm** |
| 建图（M2） | `SYS-M` P0 全过：20 m² 闭环 <0.2 m、地图可存取、重定位收敛 |
| 导航（M3） | `SYS-N` P0 全过：定点导航 ≥90%、0.3 m 停障、无碰撞 |
| 交付（M4） | 全部 P0 通过；`SYS-R` 2 h 长稳通过；户外演示通过；文档与脚本齐全 |

**安全用例（必须 100% 通过，任一失败即阻断上路）**：`SW-F01`（超时停车）、`SW-F02`（信号退出停车）、`SW-F03`（崩溃后停车）、`SYS-S02`（急停）、`SYS-S04`（雷达掉线退出导航）、`SYS-S06`（低电保护）、`CAR-B04`（舵机限位）、`SW-C05`（TF 唯一，防重复发布导致位姿跳变）。

**判定纪律：**

- 判据必须可量化（数值、频率、布尔状态），禁止"正常""基本可用"；
- 单次偶发失败不算通过，须在记录表登记重试次数；**n≥3 次全部通过**才算通过（疲劳/长稳类另行规定）；
- 任何一条用例的阈值变更，必须先改第 4 章并注明依据，不许在记录表里就地放宽。

### 2.5 环境隔离与单车排班

- **唯一真车**：同一时刻只允许一人操作实车，其余人用 mock 或 bag（设计文档 R-08）。
- **I2C 独占**：`/dev/i2c-1` 同一时刻只能被一个进程打开；跑厂商 demo 前必须停 `base_node`，反之亦然（否则事务交织，现象是随机丢指令）。
- **测试窗口**：每日固定集成窗口（建议 19:00–21:00），窗口内合并全部待测分支；窗口外只做离线测试。
- **参数快照**：每轮测试开始前 `sha256sum` 记录 `params.yaml`、`imu.yaml`、`slam_params.yaml`、`nav2_params.yaml`，写入记录表；参数不一致的两轮结果不可直接比较。
- **上电预约**：实车测试提前一天登记（时段、场地、用例集、操作人、安全员）。

### 2.6 测试数据策略

- **bag 白名单**（只录契约话题，避免录 `/image_raw` 撑爆盘）：`/scan /imu/data /odom /odom_raw /cmd_vel /cmd_vel_safe /tf /tf_static /range /line_sensor /map /diagnostics`；需要图像时单独开 `/image_raw` 并限时。
- **黄金集（golden set）**：至少三份——① 3 分钟静置（传感器噪声与零偏）；② 2 分钟直行+转向（运动学与里程计）；③ 20 m² 建图一圈（SLAM 复现）。每次改动后回放比对，阈值见 `SW-I03`。
- **数据落盘**：SSD `/mnt/ssd`（bus 3）；SSD 不可用时降级到 SD 并**缩短录制时长**（SD 寿命敏感）。
- **保留期**：缺陷相关证据保留到缺陷关闭后 6 个月；黄金集长期保留；普通回归 bag 保留 14 天。

## 3 测试环境与工装

### 3.1 软件环境准备（每次换机 / 重装后执行一次）

| 步骤 | 命令（Pi 上） | 期望 | 失败处理 |
|---|---|---|---|
| 依赖体检 | `bash tools/check_ros_deps.sh` | 21 个 dpkg 包、12 个 ROS 包、9 个 Python 模块、7 个工具均 `[ OK ]` | 按提示 `apt install ros-lyrical-<pkg>`；rplidar_ros 无 apt 包，用源码构建 |
| 硬件节点 | `i2cdetect -y 1`；`ls -l /dev/raspbot_lidar /dev/raspbot_imu /dev/video0 /dev/hailo0` | 见 0x2b、0x3c；四个设备存在 | 查 udev 规则与 `dialout`/`i2c`/`video` 组 |
| 组权限 | `groups` | 含 `i2c video dialout` | `sudo usermod -aG i2c,video,dialout ubuntu` 后重新登录 |
| 构建 | `cd ~/ros2_ws && colcon build --symlink-install` | 成功，零新增警告 | 记录警告原文，作为 `SW-S01` 失败项 |
| 频率快检 | `ros2 topic hz /odom /scan /imu/data /range` | 30 / 10 / 100 / 5 Hz（±10%） | 见 `SW-C01` |
| 电源健康 | `vcgencmd get_throttled`；`cat /sys/class/thermal/thermal_zone0/temp` | `0x0`；< 80 °C | 欠压先查电池开关与线束；`vcgencmd` 需 sudo 或 udev 规则 |
| CPU 调频 | `cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor` | `performance` | 设计文档要求；当前为 `ondemand`，见 §4.4 偏差 D-09 |

## 5 软件测试方案

软件测试的目标是"在不上真车的前提下，证明逻辑正确、接口合规、异常可控"。执行顺序固定为 `SW-S → SW-U → SW-G → SW-C → SW-I → SW-F → SW-P`，前一层不通过不进入下一层。

**通用约定：**

- 单元测试只跑在开发机上，**不需要 ROS、不需要树莓派**（`pytest` 直接跑）；
- 组件/契约/集成测试跑在 Pi 上，可用 `mock` 数据源，但必须记录硬件是否在线；
- 每条用例在记录表写：命令、参数 hash、原始输出片段、判定、重试次数。

**`SW-P04` 端到端时延测量方法（可复现，无需示波器）：**

1. 同机启动 `ros2 bag record /cmd_vel /odom`；
2. 用 5 Hz 方波发 `/cmd_vel`（0 ↔ 0.1 m/s），持续 30 s；
3. 停止后离线分析：对每个上升沿，找 `/odom.twist.linear.x` 首次超过 0.01 m/s 的消息时间戳，差值即时延；
4. 取中位数与 p95，排除前 3 个样本（节点预热）。

> 这是**软件链路时延**（发布→积分→发布），不是机械响应时延。机械响应（轮子真正转起来）只能用高速摄像或编码器测，本车无编码器，故只作为参考项，不列入判据。

## 7 实机测试方案

### 7.1 安全规程（硬性规则，违反即停止测试）

1. **第一次上电必须悬空**：四轮离地、车体垫稳、有人扶车，确认无异常转动后才落地。
2. **"轮子不转"先查电池开关**：电机电源未开时 I2C 与传感器全部正常、软件无任何判据可区分（硬件报告 §3.4）。据此排查不超过 1 min，不要先怀疑代码。
3. **两人作业**：操作人（键盘/遥控）+ 安全员（只负责断电、拔线、扶车）。安全员不得同时操作电脑。
4. **场地封闭**：清空人员与易碎物；运动方向端头留 ≥1 m 缓冲并放软挡板；S2 场地边界用锥桶围起。
5. **限速**：本轮所有实车移动测试 **≤0.30 m/s**（代码 `max_linear`）。要超过必须书面批准、单独排期，并在 S3 场地进行。
6. **禁止场景**：桌面边缘、楼梯/坡道边缘、湿滑地面、有儿童或宠物的区域、强光直射雷达的户外正午。
7. **手不离断电**：测试全程安全员手边可立即断开电池/电机电源；异常（异响、异味、冒烟、轮子不停、车体过热）**先断电再排查**。
8. **单一速度源**：同一时刻只允许一个 `/cmd_vel` 发布者。开测前 `ros2 topic info /cmd_vel` 确认 Publisher count = 1。
9. **带电不插拔**：USB/I2C 线插拔一律断电进行；例外仅限悬空状态下的故障注入用例（`SW-F05`、`SW-F06`），且需安全员在场。
10. **电池纪律**：电压 <6.6 V 禁止建图与录包（BMS 过放会切断并损坏文件系统）；充电时不得开机测试。

**标定公式与注意事项：**

- `CAR-C01` 的关键：**`/odom` 不能作为距离真值**。因为 `/odom` 由指令速度积分，命令 0.15 m/s × 4 s 一定得到 0.600 m，无论车实际走了多少。必须用卷尺（或地面标记）量真实位移。这也是本方案反复强调"开环里程计不可当真值"的原因。
- `CAR-C02` 用 IMU 的 yaw 差作真值，前提是 `CAR-C04` 已完成、且车在水平地面（HWT101 只测 Z 轴，倾斜会引入误差）。
- 速度标定受电量影响（满电与半电可差约 3%），**标定应在满电（≥7.8 V）下进行并记录电压**；后续测试若电压差异 >0.5 V，需注明。
- 舵机与雷达的机械安装一旦改动（换支架、重新拧紧），`CAR-C04`、`CAR-C05` 必须重做。

### 7.5 运动精度（CAR-M，场地 S1/S2）

## 8 缺陷管理与准出

### 8.1 严重度定义

| 等级 | 定义 | 示例 | 处理时限 |
|---|---|---|---|
| S1 致命 | 安全问题、数据损坏、可复现的失控 | 轮子不停、TF 双发布导致飞车、地图/参数丢失 | 立即停止测试，当天定位 |
| S2 严重 | 核心功能不可用、指标严重超标 | 直行 2 m 偏 30 cm、导航成功率 <50%、IMU 拔线崩溃 | 48 h 内给出修复计划 |
| S3 一般 | 单项指标不达标、有规避手段 | 频率偏差 15%、时序抖动偏大、日志刷屏 | 当个里程碑内修复 |
| S4 轻微 | 体验、文档、诊断信息 | 报错信息不清晰、README 缺项 | 可排入下个版本 |

### 8.2 缺陷单必填字段

`编号`、`标题`、`严重度`、`发现阶段与用例ID`、`环境（§3.5 全字段）`、`复现步骤（可复制命令）`、`预期 vs 实际`、`证据（bag/日志/截图路径）`、`影响面（哪些用例受影响）`、`责任人`、`状态`。

### 8.3 回归与关闭

- 修复后**必须用原用例复测**，并补一条回归用例（放进 `SW-U` 或黄金集）；
- 关闭条件：原用例通过 + 相关用例未被破坏 + 证据齐全；
- S1/S2 缺陷关闭需测试负责人确认，其余由属主确认；
- 每个里程碑结束时统计：新增/关闭/遗留缺陷数，遗留 S1/S2 必须为 0 才能进入下一里程碑。

### 8.4 准出判定

| 检查项 | 要求 |
|---|---|
| P0 用例 | 100% 通过 |
| P1 用例 | ≥80% 通过，未通过项有批准的缺陷单与规避措施 |
| P2 用例 | 可延后，登记技术债 |
| 安全用例 | 100% 通过（见 §2.4 列表），任一失败即阻断上路 |
| 文档 | 参数、地图、launch、标定表全部纳入版本管理；本方案附录 C 记录表齐全 |
| 可复现 | 在全新 Ubuntu 26.04 上按 README 重建通过（NFR-07） |
