# 手机遥控 RASPBOT-V2 可行性分析（iPhone + 微信小程序路线）

- 版本：v1（分析稿，不含代码）
- 日期：2026-11-19
- 分析对象：RASPBOT-V2 / Raspberry Pi 5（`192.168.50.98`，Ubuntu 26.04 + ROS 2 Lyrical），控制端为 iPhone
- 依据：`docs/硬件全面测试报告_2026-11-19.md`（实测）、`ros2_ws/src/raspbot_base`（现有节点）、微信开放文档（平台规则）
- 说明：撰写时 Pi 未上电（LAN 内 ping/22 端口不通），凡标「待实测」的项需上电后按 §9 验证；其余硬件数据均来自 11-19 实测报告

## 0. 结论

**可行，而且不需要上架、不需要备案、不需要域名、不需要买服务器、不需要苹果开发者账号。** 用「个人主体小程序 + 体验版 + 局域网直连」这一组合，全部成本为 0 元，代码量约 1000 行以内，预计 3–4 人日可到「手机推摇杆、车按方向走、状态回显」的可用状态。

但有三个必须先说清楚的边界：

1. **小程序只适合当「遥控器 + 状态面板」，不适合当「图传终端」。** 个人主体小程序**用不了** `web-view`（不能嵌 H5 当视频窗）、**用不了** `live-player`（不能放 RTMP/HLS 低延迟直播），视频只能走「JPEG 帧 + canvas 解码」，实测上限约 8–12 fps、延迟 150–300 ms。够开慢速车，不够做第一视角竞速。
2. **一旦要求「4G 环境下远控」（车在小区里跑、人在外面），方案性质就变了**：必须上云中转 + 已备案域名 + 云服务器，工作量和成本各上一个台阶。局域网/热点范围内用，才是小程序方案的最优区间。
3. **真正的最快路径其实是 H5**（手机浏览器打开一个页面，扫码即用，可「添加到主屏幕」），视频直接用 MJPEG 就能跑 25–30 fps，1 人日能出原型。小程序的唯一优势是「不用记地址、不用装 App、微信里点一下」，如果这个体验对你不是刚需，H5 更划算。

**建议路线：先用 H5 半天验证链路与手感 → 确认可用后，把同一套 UI 平移成小程序（体验版）。** 两者共用 Pi 端同一个 WebSocket 服务，不重复投入。

## 1. 需求与现状

### 1.1 需求假设（需你确认，见 §11）

| 编号 | 假设 | 影响 |
|---|---|---|
| R1 | 手机与车在**同一局域网**（家里 WiFi 或 iPhone 热点），作用距离 10–50 m | 决定是否要云中转 |
| R2 | 控制方式是**连续速度遥控**（前后/横移/自转），不是「点一下走 1 米」 | 决定能否绕开无编码器的限制 |
| R3 | 需要**视频**，但可接受 10 fps 级别的「看得见路」画质 | 决定视频方案，是小程序路线的最大约束 |
| R4 | 单人自用，不需要多用户/权限体系 | 决定安全设计可以做到最简 |

若 R1 不成立（需要 4G 远控）或 R3 要求 25 fps 以上流畅视频，请直接看 §3 的方案 B / C，结论会变。

### 1.2 现状盘点：已经有什么、缺什么

| 层 | 现状 | 结论 |
|---|---|---|
| 底盘执行 | I2C 0x2B 全部验证通过：4 电机、2 舵机、RGB、蜂鸣器、超声、循迹、IR；单次 I2C 事务 0.32 ms | ✅ 够用 |
| ROS 2 控制面 | `raspbot_base` 已建好：订阅 `/cmd_vel`，发布 `/odom`(30 Hz)、`/range`(5 Hz)、`/line_sensor`(5 Hz) | ✅ 手机侧只需对接 `/cmd_vel` |
| 传感器 | `/scan` 10 Hz（RPLIDAR C1）、`/imu/data` 100 Hz（HWT101，静态 yaw 漂移 0.0022°/min） | ✅ 可做状态面板/避障提示 |
| 摄像头 | USB UVC `/dev/video0`，MJPG 640×480@30、720p@30 实测 28–29 fps；单帧 640×480 JPEG 83.8 KB | ✅ 视频源现成 |
| 算力余量 | base_node 6.6% CPU、imu_node 9.7%、lidar 1.7%；内存 7.7 GiB 用 0.6；SoC 41–44 °C，`throttled=0x0` | ✅ 再加一路视频编码无压力 |
| 网络服务 | **无**：Pi 上没有任何 HTTP/WebSocket 服务 | ❌ 需新增（本方案唯一的新增组件） |
| 手机端 | 无 | ❌ 需新增（小程序或 H5） |
| 电量检测 | 板载**无**电压/电流采样 | ⚠ 状态面板做不了「真实电量」 |
| 轮速反馈 | 板载**无**编码器，`/odom` 是开环积分 | ⚠ 不能承诺精确走位，只能做速度遥控 |

**一句话：车这一侧已经具备被遥控的全部条件，缺的只是一个「把手机指令翻译成 `/cmd_vel`」的桥。**

## 2. 三条平台事实，决定了方案边界

### 2.1 小程序的网络规则：默认很严，但对局域网 IP 开了口子

官方规则（[网络 / 使用说明](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)）：

- 小程序只能与**已配置的服务器域名**通信，域名必须 **HTTPS / WSS** 且**已 ICP 备案**，**不能是 IP**；
- **但**：从基础库 2.4.0 起，网络接口**允许与局域网 IP 通信**（仅禁止与本机 IP 通信）——即 `http://192.168.50.98:8080` 这类地址属于规则内的例外。

这条例外是整个方案的支点：**不上架就不需要域名、不需要备案、不需要证书。**

> ⚠ 该例外在不同机型/基础库上存在行为差异，社区里既有「体验版直接能连局域网 IP」也有「必须开调试才行」的案例。因此 §9 把它列为**第一优先验证项**，并有兜底（见 2.3）。

### 2.2 个人主体小程序的两条硬性能力缺失

| 能力 | 个人主体 | 后果 | 对策 |
|---|---|---|---|
| `web-view`（内嵌网页） | **不支持**（官方文档：「个人类型的小程序暂不支持使用」） | 不能在小程序里塞一个 H5 页面来放 MJPEG/WebRTC 视频 | 视频只能自己用 canvas 渲染 |
| `live-player` / `live-pusher`（直播组件） | **不支持**（仅开放给企业等非个人主体，且需特定服务类目） | 不能走 RTMP/HLS 低延迟直播 | 同上；HLS 可用 `video` 组件但延迟 2–5 s，遥控不可用 |

> 这两条是「视频只能做到 8–12 fps」的根本原因，不是实现水平问题，换谁都绕不过去。

### 2.3 不上架，「体验版」就是你的私人通道

| 项 | 事实 | 对本项目的意义 |
|---|---|---|
| 上架门槛 | 发布/上架需**小程序备案**（2023-09 起）、HTTPS 域名、类目审核 | **我们不上架**，全部绕过 |
| 开发版 | 开发者工具「预览」二维码，**有效期约 25 分钟** | 只适合开发调试 |
| 体验版 | 上传后在后台「设为体验版」，**二维码长期有效** | ✅ 日常使用就用它 |
| 体验成员 | **最多 15 人**，可随时增删 | 天然的访问白名单，别人扫码也进不来 |
| 域名校验绕过 | 体验版内点右上角「···」→「打开调试」→ 不校验合法域名/证书，可用 http 和 IP | 兜底手段，已验证在社区广泛可用 |
| 账号成本 | 个人主体注册免费（邮箱 + 身份核验），无需认证、无需年审 | 0 元 |
| 工具 | 微信开发者工具 Windows/macOS 客户端，免费 | 现有 Windows 环境即可 |

**结论：把「小程序」当私人遥控器用，平台侧的门槛基本归零。**

### 2.4 iOS 特有的两个坑

1. **本地网络权限**：iOS 13+ 对 App 访问局域网有独立开关。微信若未获授权，请求 `192.168.x.x` 会直接失败。位置：`设置 → 隐私与安全性 → 本地网络 → 微信`。这是 iPhone 上「开发者工具里好好的、真机就是不通」的头号原因。
2. **小程序切后台即挂起**：小程序进入后台约 5 s 后逻辑层挂起，WebSocket 断开；锁屏同理。这是**双刃剑**——好处是「手机一锁屏车必停」，坏处是「看一眼消息回来要重连」。必须做：心跳 + 自动重连 + 服务端看门狗 + `wx.setKeepScreenOn`。

## 3. 候选方案对比

评分：★=1 分，满分 5 星（分数越高越好）

| # | 方案 | 延迟 | 视频 | 免装 App | 成本 | 工作量 | 适用场景 |
|---|---|---|---|---|---|---|---|
| A | **小程序 + 局域网 WS 直连**（推荐 v1） | ★★★★★ 25–90 ms | ★★☆ 8–12 fps | ✅ | 0 元 | 3–4 人日 | 家里/楼下/热点范围内 |
| B | 小程序 + 云中转（MQTT/WSS） | ★★★ 150–400 ms | ★★☆ | ✅ | 云服务器+域名+备案 | 6–9 人日 | 4G 异地远控 |
| C | **H5 网页 + WS + MJPEG**（推荐先做） | ★★★★★ 100–200 ms | ★★★★★ 25–30 fps | ✅（浏览器/加到主屏） | 0 元 | 1–2 人日 | 同上，体验最好 |
| D | 原生 iOS App | ★★★★★ | ★★★★★ | ❌ 需安装 | 免费签名 7 天过期 / 开发者账号 ¥688/年 | 5–8 人日 | 不推荐 |
| E | rosbridge + 现成 Web 前端（rosboard/roslibjs） | ★★★ | ★★★ | ✅ | 0 元 | 1–2 人日（若编译顺利） | 看数据可以，遥控 UI 不适配手机 |
| F | 微信云托管做中继 | — | — | — | 按量 | — | ❌ **排除**：官方限制「仅支持 HTTP，不支持 TCP/UDP/MQTT」 |

### 各方案一句话结论

- **A**：最贴合你「小程序 + iPhone + 不装 App」的原始诉求，链路最简单，延迟最低，唯一短板是视频帧率。
- **B**：能解决 4G 远控，但要买服务器、备案域名、配 WSS 证书，且多一跳中转，操控手感明显变钝；**除非确实需要异地，否则不建议现在做**。
- **C**：技术上是 A 的「去掉小程序外壳」版本，视频能力直接拉满。**建议作为第一天的验证手段**，也作为小程序视频不够用时的备选。
- **D**：iOS 侧分发是硬伤（免费证书 7 天重签、TestFlight 需审核），已排除。
- **E**：`rosbridge_suite` 在 ROS 2 Lyrical 上未必有现成二进制包，需源码编译；且它面向「可视化」而非「低延迟遥控」，指令走 JSON 文本+CDR 转换，反而更慢。可以作为调试期看话题的工具，不作为产品路径。
- **F**：微信云托管官方明确只支持 HTTP、不支持长连接协议，做不了实时遥控通道。

## 4. 推荐架构（方案 A）

### 4.1 拓扑

```
┌──────────────── iPhone (iOS 17+) ────────────────┐
│ 微信 → 小程序「RASPBOT 遥控」(体验版, 成员白名单)  │
│   ├─ 虚拟摇杆 / 方向键   touch → 20 Hz 控制帧     │
│   ├─ 急停按钮（大红键）+ 松手即停                 │
│   ├─ canvas 视频窗（JPEG 帧，8–12 fps，可关）     │
│   └─ 状态面板：yaw、超声距离、循迹、CPU/温度       │
└──────────────────┬───────────────────────────────┘
                   │ 同一 WiFi，或 iPhone 个人热点
                   │ ① ws://192.168.50.98:8765   控制+遥测（小帧，独立连接）
                   │ ② ws://192.168.50.98:8766   视频（大帧，可关闭）
                   ▼
┌───────────────── Raspberry Pi 5 ─────────────────┐
│ remote_bridge（Python 3 + asyncio，新增 ~400 行） │
│   ├─ token 鉴权 / 单客户端占用 / 心跳              │
│   ├─ 看门狗：400 ms 无控制帧 → 发布零速           │
│   ├─ 控制 → /cmd_vel 20 Hz                        │
│   ├─ 动作 → /servo_pan /servo_tilt /led /buzzer   │
│   ├─ 遥测 ← /odom /range /line_sensor /imu/data   │
│   │        （降采样后 10 Hz 下发）                 │
│   └─ 视频：/dev/video0 → 缩放到 480×360 → JPEG    │
│                                                    │
│ raspbot_base（已存在，rclpy）← /cmd_vel            │
│   └── I2C 0x2B（0.32 ms/事务）→ 4×电机/2×舵机     │
└────────────────────────────────────────────────────┘
```

关键设计原则：

- **remote_bridge 不碰 I2C。** 它只发 `/cmd_vel`，由 `raspbot_base` 独占 `SMBus(1)`。这避免了「厂商库和 ROS 节点抢总线」的老问题（`raspbot-v2` 技能里记过这个坑）。
- **控制与视频分两条 WebSocket。** 单条 TCP 上 30 KB 的视频帧会阻塞后面的控制帧（队头阻塞）：2 Mbps 下 30 KB 要 120 ms，正好落在手感敏感区间。分开后控制通道始终 <5 ms。小程序允许 5 条并发 WS，够用。
- **视频可一键关闭。** 弱网时关视频，操控优先。

### 4.2 数据通道定义（供后续实现参考）

| 通道 | 方向 | 频率 | 载荷 | 单帧大小 |
|---|---|---|---|---|
| 控制 | 手机 → Pi | 20 Hz（触摸变化立即发） | `{vx, vy, wz, seq, ts}` | ~40 B |
| 动作 | 手机 → Pi | 事件触发 | `{type: stop/servo/led/beep/…}` | 20–40 B |
| 遥测 | Pi → 手机 | 10 Hz | `{yaw, range, line, scan_min, cpu, temp, watchdog}` | 150–300 B |
| 视频 | Pi → 手机 | 8–12 fps | 二进制 JPEG（通道头 1 B） | 25–35 KB（480×360, q60） |

### 4.3 与现有 ROS 2 的接口（无需改动 `raspbot_base`）

| 需要的能力 | 用哪个话题 | 现状 |
|---|---|---|
| 前进/横移/自转 | publish `/cmd_vel` | ✅ 已实现，30 Hz 执行 |
| 云台 | `/servo_pan` `/servo_tilt` | ✅ 已实现（**上层必须 clamp：pan 0–180，tilt ≤110**，厂商库限位代码是无效的） |
| 灯 / 蜂鸣器 | `/led` `/buzzer` | ✅ 已实现 |
| 姿态显示 | subscribe `/imu/data` | ✅ 100 Hz，取 yaw 即可 |
| 前方距离 | subscribe `/range` | ✅ 5 Hz（注意上电前 0.3 s 数据偏小约 300 mm） |
| 循迹 | `/line_sensor` | ✅ 5 Hz |
| 简易雷达图（可选） | `/scan` | ✅ 10 Hz，小程序端画 360 点扇面即可 |

**结论：Pi 侧不需要改现有节点，只新增一个独立进程。**

### 4.4 安全与失效保护（必须做，不能省）

| 机制 | 做法 | 为什么必须有 |
|---|---|---|
| 看门狗 | 400 ms 无控制帧 → `/cmd_vel` 零速 | 手机没电/走出 WiFi 范围，车不能一直跑 |
| 断连即停 | WS 关闭回调里立即停车 | 同上，覆盖优雅断开 |
| 松手即停 | 摇杆 `touchend` 发零速 | 避免「松手后按最后速度巡航」 |
| 急停按钮 | UI 常驻大红键，同时发停车 + 关灯 | 视觉/雷达判断失误时的最后手段 |
| 单客户端占用 | 第二个连接进来时踢掉旧的或拒绝 | 防止两台手机同时抢控制 |
| 配对码 | 首次连接输入 Pi 屏幕/日志上的 6 位码，换取 session token | 体验版本身有白名单，这层是防「同一 WiFi 下别人也装了开发者工具」 |
| 只绑局域网 | 服务只监听内网地址，不做公网端口映射 | 家里路由被扫的风险远大于收益 |
| 上电默认停 | 服务启动与节点退出路径都发零速 | `raspbot-v2` 技能里的硬性要求 |

**安全模型说明**：不上架的小程序只有 15 个体验成员能打开，这本身就是一层很强的访问控制；再加 token，足够个人使用。不需要做账号体系。

## 5. 性能预算

### 5.1 端到端操控延迟（方案 A，同 WiFi）

| 环节 | 典型 | 最坏 | 依据 |
|---|---|---|---|
| 触摸采样 → 发帧 | 16–50 ms | 50 ms | 20 Hz 发送节流 |
| WiFi 空口往返（同 AP） | 2–10 ms | 30 ms | 家用 5 GHz |
| 热点模式往返（iPhone） | 5–20 ms | 50 ms | 手机做 AP |
| bridge 解析 + 发布 | 1–3 ms | 5 ms | 纯 Python 小 JSON |
| `base_node` 定时周期 | 0–33 ms | 33 ms | 30 Hz |
| I2C 写 4 轮 | ~1.3 ms | 3 ms | 单片 0.32 ms 实测 |
| **合计** | **25–90 ms** | **~150 ms** | 人感知阈值约 150 ms，可接受 |

对比：4G 云中转（方案 B）仅「手机↔云↔车」两跳就 100–300 ms，加视频回传抖动，手感会明显发飘。

### 5.2 视频带宽（关键取舍）

| 参数 | 单帧 | 10 fps | 20 fps | 评价 |
|---|---|---|---|---|
| 640×480, q60（重编码） | 25–35 KB | 2–3 Mbps | 4–6 Mbps | ✅ 推荐 |
| 480×360, q60 | 12–18 KB | 1–1.5 Mbps | 2–3 Mbps | ✅ 弱网/省 CPU |
| 640×480 原生 MJPG（不重编码） | 83.8 KB（实测） | 6.7 Mbps | 13 Mbps | ⚠ 可用但浪费 |
| 1280×720, q60 | 60–80 KB | 5–6 Mbps | 10–13 Mbps | ⚠ 小程序端解码压力大 |

结论：**480×360 或 640×480 + q60 + 10 fps** 是甜点，2–3 Mbps 在 WiFi 上毫无压力，iPhone 端 base64 解码也不吃力。

## 6. 视频：小程序路线的真实上限

小程序里能走的三条路，只有第一条值得做：

| 方案 | 小程序可用 | 延迟 | 帧率 | 工作量 | 结论 |
|---|---|---|---|---|---|
| **JPEG 帧 + `canvas` 渲染**（WS 二进制 → base64 → `canvas.createImage`） | ✅ | 150–300 ms | **8–12 fps** | 1–1.5 人日 | ✅ 推荐 |
| `<image>` 组件逐帧换 URL（每帧一次 HTTP 请求） | ✅ | 200–400 ms | 5–8 fps | 0.5 人日 | 备选，闪烁明显 |
| HLS + `video` 组件 | ✅ | **2–5 s** | 25–30 fps | 1 人日 | ❌ 遥控不可用 |
| `live-player`（RTMP/FLV） | ❌ 个人主体不支持 | — | — | — | ❌ 排除 |
| `web-view` 嵌 H5 页面 | ❌ 个人主体不支持 | — | — | — | ❌ 排除 |
| **MJPEG（H5，Safari/微信内置浏览器）** | 非小程序 | 100–200 ms | **25–30 fps** | 0.5 人日 | ✅ H5 路线用 |
| **WebRTC（H5）** | 非小程序 | 80–200 ms | 30 fps | 1–2 人日 | 追求画质时再上 |

**判断**：如果遥控场景是「看着路慢慢开（室内、院子、人行道）」，8–12 fps 完全够用；如果要做「第一视角快速穿行」，小程序不是合适的容器，应该走 H5 + MJPEG/WebRTC。

## 7. 工作量与里程碑

| 阶段 | 内容 | 人日 | 验收标准 |
|---|---|---|---|
| **0** | 注册个人小程序 + 开发者工具建空项目 + 打通 `wx.request` 到 `http://192.168.50.98:8080/health` | 0.5 | 手机上看到 Pi 返回的 JSON（这一步就把最大未知数消掉） |
| **1** | Pi 端 `remote_bridge`（WS + `/cmd_vel` + 遥测 10 Hz）+ 小程序摇杆 UI | 1.5–2 | 推摇杆车按方向动（**架空**测试）；松手/断网 0.4 s 内停 |

**v1（0–2 阶段）合计 3–4 人日**，其中阶段 0 的风险最高、收益最大，应该第一个做。

### 成本

| 项 | 方案 A（局域网） | 方案 B（4G 远控） |

## 10. 明确不建议做的事

1. **不要为了「能远程」去上架小程序**：备案 + 类目审核 + HTTPS 域名，周期以周计，且「个人主体 + 遥控类硬件」的类目未必过审，收益为零。
2. **不要用 `web-view` 或 `live-player` 规划视频**：个人主体根本用不了，写到设计里就是返工。
3. **不要用微信云托管做实时通道**：官方只支持 HTTP，不支持 TCP/UDP/MQTT 长连接。
4. **不要在小程序里做「精确走 1 米 / 定点转向」**：无编码器，`/odom` 是开环积分，打滑就失真。要做就加编码器或依赖 IMU+雷达做闭环。
5. **不要让 bridge 和 `base_node` 同时打开 I2C**：总线只有一个主人。
6. **不要把 Pi 的 8765 端口映射到公网**：没有鉴权时等于把车交给整个互联网。
7. **不要先做 UI 再验证链路**：先花半天跑通 V1–V4，再谈界面。

## 11. 需要你确认的三件事

1. **使用场景**：室内/楼下院子（WiFi 或热点够用），还是要在外面用 4G 远控？——决定 A 还是 B。
2. **视频的硬要求**：能接受 8–12 fps「看得清路」，还是必须 25 fps 以上流畅？——决定小程序还是 H5。
3. **「微信小程序」是硬需求吗**：如果「手机扫码/加到主屏就能开」即可，H5 能省一半工作量、视频好一倍。
